Working name: AI Risk Review.

Downloadable first release.

AI Risk Review v0.4 is a Windows-first local checkup, packaged as an executable that opens a guided browser interface on this computer.

The current release checks traditional installations, current-user Windows packages, independently running AI applications and recognized local TCP listeners. It reconciles these into a tool inventory and includes a terminal executable. Selected MCP JSON and Codex TOML settings, and fixed tool-directory presence checks, are explicit opt-ins. It includes a structured optional questionnaire, richer package / connection facts, evidence-based findings, HTML/JSON downloads and comparison with an imported earlier report.

Run it: extract ai-risk-review/releases/AI-Risk-Review-v0.4.1-windows-x64.zip and launch AI-Risk-Review.exe. Source, tests and build instructions are in ai-risk-review/.

This release requires no Python installation, Docker, account or model download. There are no subnet probes or automatic changes. Generic ports do not identify AI; unknown and inaccessible checks stay visible. A missing finding is not automatically resolved.

Current limits: unsigned development preview, narrow tool signatures, English Windows listener output, no organization-wide SaaS discovery and no independently reviewed compliance conclusion. Read the README and SECURITY document before sharing results.

Distinctive direction: understandable evidence, honest uncertainty and before/after checks. Related open-source discovery tools already exist; no first-of-its-kind claim is made. Source repository and v0.4.1 prerelease are available on GitHub. Code signing and broader compatibility testing remain release work.

v0.4: an evidence workspace for nontechnical users

The app now uses the supplied white, blue and navy dashboard reference. v0.4.1 also adds System / Light / Dark appearance choices with a preference that persists across local launcher ports. Collection coverage and evidence counts replace unsupported safety percentages. Overview, inventory, evidence, readiness and U.S. sources have dedicated navigation.

  1. Add one optional use-case profile, including role, purpose, area and affected states.
  2. Review relevant follow-up questions, preserving unsure answers.
  3. Select policy, vendor or assessment files explicitly. Supported text, Markdown, HTML, DOCX and text-based PDF are parsed locally with bounds. Candidates cite physical page, paragraph or line references; matches remain unverified.
  4. Opt into connection names only when appropriate. Commands, arguments, full URLs and credentials remain excluded.
  5. Review prioritized actions and follow compact references to the evidence library.
  6. Save a local report or share-safe report without connection labels, profile or document names / excerpts.

Documents: up to six, 1 MB each / 4 MB total, with an isolated bounded parser. No OCR, encrypted files or embedded content execution. Keep both executables together. One review covers one use case. The 12-source catalog remains selected, dated and offline.

Evidence first, then an applicable crosswalk.

The goal is to gather useful evidence and map it to current U.S. AI frameworks, laws and policies. v0.4 implements the first selected catalog: 12 primary-source entries and 12 authored evidence work packages. It is not an exhaustive U.S. legal catalog or the full NIST framework.

  1. Discover: read supported local installation, process, listener and optional configuration facts without exporting credentials.
  2. Establish context: ask optional yes/no/unsure questions about affected states, federal work, employment, consequential decisions, consumers and health data.
  3. Link evidence: identify report-local observation IDs and keep self-reported statements separate from observed facts.
  4. Crosswalk: show source type, date, scope, review trigger and mapped NIST provisions / other topic associations. A framework is not automatically a legal obligation.
  5. Request what is missing: specify the deliverable, owner role and verification needed for each work package.
  6. Review and maintain: preserve unknowns, review applicability and evidence with qualified owners, and recheck changing source material.

The initial registry covers NIST AI RMF / GenAI Profile, three OMB memos, selected FTC / EEOC / HIPAA issues, Colorado SB26-189, California ADMT regulations, Texas HB149 and NYC Local Law 144. Sources were reviewed October 19, 2026; the offline snapshot flags a review overdue after 30 days. It does not check the internet automatically or certify compliance.

Expansion required for broader U.S. coverage

  • Explicit selection of policy and assessment documents, with page / section references and evidence review states.
  • A per-use-case inventory covering developer / deployer roles, all affected jurisdictions, data classes and sector-specific thresholds.
  • Additional state, local and sector packs, plus contracts and internal policies; international standards used in the U.S. need separate mappings.
  • A reviewed update process that tracks new, amended, repealed, proposed and future-effective provisions and can identify affected evidence requests.
  • Optional authorized enterprise connectors to reconcile browser / SaaS / API use beyond the local computer.

These expansions remain future work. Automatic discovery and automated mappings help prepare a review; business practices, model behavior and legal applicability still need supporting evidence.

Longer-term service workflow

Build an analyst-assisted AI inventory and risk review tool. Use it to understand a client’s AI use, identify supported concerns and produce a practical action plan with named owners.

Start with the AI review service you want to provide. The original OpenSource AI Risk Scanner blueprint is an early concept; this plan revises its collection method, assessment logic and reporting claims.

Discover actual use before assessing risk

A port scan can identify possible local services. It misses browser-based AI, personal accounts, embedded assistants and many cloud integrations. An open port does not establish that a service is AI, that its use is unauthorized or that sensitive data is involved.

The first version should import existing records and combine them with a short questionnaire. Record what each source can and cannot show.

Inputs for the first version
InputWhat it helps establish
Management and staff questionnaireTools, purposes, informal use and responsible people.
Approved-software list and purchasing recordsKnown products, account tiers, ownership and commercial relationships.
Available identity, endpoint and web-filter exportsAdditional applications and observed activity, within the source’s visibility and retention limits.
Vendor terms and account settingsRetention, training use, access permissions and contractual protections.
Policies and training recordsWhat employees have actually been told and which processes are documented.

Missing activity in an export is not proof that nobody uses the tool. Keep network discovery as an optional, authorized module for clients with local AI infrastructure.

Organize the inventory around use cases

“ChatGPT” is too broad an entry. “Accounting staff use a particular account tier to summarize customer invoices” identifies a workflow, data and people that you can review.

  • Product, account tier and business owner.
  • Purpose and affected business workflow.
  • Data categories involved.
  • Relevant settings, integrations and permissions.
  • Approval status and supporting evidence references.
  • Known gaps, unanswered questions and review date.

Keep the approval decision separate from the strength of the evidence. An approved tool can still have unverified settings or a newly introduced use case.

Evidence states
StateMeaning
ReportedA person describes the practice; it has not yet been independently observed.
ObservedA record or setting was inspected. Its date and scope are recorded.
VerifiedA defined check supports the specific claim within the stated scope. Record who checked it and how.
UnknownThe available information does not support a conclusion. Keep the question open.

Use explicit rules for supported findings

Replace model-generated risk scores with checks whose logic you can explain. Each finding should reference its evidence, describe the affected use case and distinguish what is established from what remains uncertain.

  • Sensitive information enters a tool without an approved data-handling decision.
  • An integration has broader access than its task requires.
  • No person owns the account or reviews access.
  • Consequential output is used without verification.
  • Vendor retention or training terms have not been reviewed.

Initially, report findings by priority and evidence coverage. Establish a documented prioritization rubric; do not imply that a model has measured the organization’s compliance. NIST AI RMF is a voluntary risk-management framework and does not supply the original blueprint’s universal 0–100 scoring method.

Illustrative finding record

Observation
Staff report using a personal AI account to summarize customer invoices.
Evidence
Interview record E-014. No account-settings review is available.
Concern
Approval and data-handling conditions are unverified; actual retention and training settings remain unknown.
Next action
The workflow owner reviews the product, account tier, settings and permitted data before approving continued use.
Closure proof
Recorded approval decision, relevant settings evidence and confirmation that staff received the permitted-use instructions.

Framework mappings should be curated, versioned references attached to supported findings. Keep EU AI Act applicability out of automatic scoring; any later assessment needs the actual use case, organizational role, jurisdiction and applicable requirements.

Let local AI draft explanations

Ollama can summarize findings, explain them in plain language and draft remediation descriptions. Explicit rules and your review process determine which findings are supported.

  • Send only selected, necessary evidence to the model.
  • Require references to evidence records and validate that those records exist.
  • Use a JSON schema and validate returned types, values and required fields.
  • Treat imported text as untrusted evidence. Instructions inside a document must not control the assessment.
  • Keep the model’s draft separate from the reviewer’s approved conclusion.
  • Review every client report before release.

A model outage should leave the evidence and rule results intact. Display “draft unavailable” and allow manual completion. Do not convert a failed request into a numerical risk score.

Structured output helps constrain format; it does not establish that a statement is true. Select the local model after evaluating it against representative review examples and the available hardware. Local execution still has hardware, operating and maintenance costs.

Keep the first implementation local and small

Use a Python application with file imports, local evidence records, explicit review rules and an optional drafting step. Start with a CLI or simple local workflow you can operate reliably; add a larger interface after the workflow is proven.

Privacy is a deployed behavior to verify

Keep inference internal, disable cloud features, control outbound traffic and test the deployed configuration before claiming that review data stays local. Ollama documents OLLAMA_NO_CLOUD=1. Downloads and updates need to be distinguished from assessment processing.

Collect proportionate evidence, redact unnecessary sensitive content and define storage, retention, export and deletion practices. Local deployment alone does not establish that an environment is suitable for patient information, controlled defense data or other restricted records.

Build in the order the service needs it

  1. Deliver two small pilot reviews manually. Use the same questionnaire, inventory and finding structure. Produce an AI inventory, supported findings, approved-use recommendations and an action register. Measure where your time goes.
  2. Automate imports and records. Validate files, normalize use cases, retain evidence references and preserve unknowns. Keep a usable workflow without an LLM.
  3. Add repeatable checks and reporting. Turn recurring review questions into explicit rules. Generate a report with scope, evidence, findings, owners, limitations and review approval.
  4. Add local drafting. Evaluate whether the model saves time without introducing unsupported claims. Keep manual review and a working failure path.
  5. Add discovery integrations selectively. Build a connector only when repeated engagements show that its data improves coverage or saves meaningful effort. Add authorized local-network discovery where clients actually need it.

Client deliverables

  • An AI tool and use-case inventory, with approval and evidence status.
  • Evidence-backed findings and unresolved questions.
  • Approved-use recommendations, including data restrictions and output review.
  • An action register with an owner, priority, target date and closure evidence for each action.
  • A reviewed report explaining scope, collection limits and what was checked.

These deliverables support the AI review service. Access changes, endpoint controls, incident investigation and specialist legal assessments require separately agreed responsibilities and qualified personnel.

Define what the first version must demonstrate

  • A pilot can be completed from approved inputs to a reviewed report without requiring the model.
  • Every finding links to evidence, identifies its scope and exposes unanswered questions.
  • Incomplete imports and model failures remain visible; they do not become safe or medium-risk results.
  • A non-AI service on a common port is not automatically identified as AI or unauthorized use.
  • Generated explanations cannot silently replace approved findings or review decisions.
  • Client records remain separated, and export, retention and access behavior are checked.
  • The HTML report remains readable on screen and when printed.
  • Pilot measurements show which automated steps reduce preparation or review time.

Decisions to settle before implementation

Confirm the initial client segment, available export sources, operator hardware, retention needs and rule rubric. Treat the name AI Risk Review as a working app name. Revisit the architecture if this becomes a shared web service, collects directly from client accounts or handles data requiring a specially approved environment.
